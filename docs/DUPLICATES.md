# 重复原音检测

## 会检测什么

从0.3.2起，上传时按原始文件字节的SHA256检查相同原音。即使换了歌名或文件扩展名，字节完全相同仍会提示已有曲目；已启用、未开放草稿和旧版原音都参与检查。

重复不会生成第二份原音，不会覆盖、改名、删掉或合并旧曲目，也不会自动修改别名、说明和启停状态。管理页显示已有原音及状态，点击“查看”会刷新、搜索并突出显示原曲目，不会自动打开设置或启用草稿。

同名不同字节仍是同名冲突，不能覆盖。字节不同的文件允许另外上传，不因为歌名相近就删除或合并。

## 明确边界

这是文件去重，不是声学指纹：不同编码、采样率、ID3标签或不同版本，即使听起来是同一首歌，也不保证检出。SHA256与路径只用于本机校验，不出现在聊天歌单或重复提示中，不向外部服务发送音频，不调用模型或产生生图/语音费用。

不会清理已经存在的重复歌曲。需要管理员自行核对来源、版本及使用授权；软件不能确认音频来源或分发权。

## 小内存与变化检测

- 每次最多读取64KB，单文件仍限制50MB；先比较体积，只读取可能相同的原音。
- 每个曲库实例最多缓存501个文件状态与摘要，不持久化缓存、不保存整段音频。
- 列表、搜索、聊天匹配与点歌不会为了去重重新读取全部音频。只在上传预检及最终入库时检查。
- 缓存命中需同时核对文件身份、大小、修改与变化时间；Windows还读取原生ChangeTime，避免Python旧版本只提供创建时间的问题。
- 文件最近3秒内发生变化或时间值在将来时，不信任元数据缓存，重新流式读取，防止快速连续写入的时间值合并。稳定文件才复用摘要。
- 上传预检在音频解析前执行；解析后、真正入库前再次检查。并发上传及重命名、删除、编辑在同一插件实例内串行，入库仍采用独占硬链接，不覆盖同名文件。

不支持多个机器人进程或其他程序并行修改同一个数据目录。外部变更被发现时拒绝本次上传，要求刷新核对；这不是抵御有权限恶意修改文件、伪造元数据或回退系统时钟的完整性认证方案。

## API结果与原生Bridge

旧入口`page/songs/upload`保持重复时HTTP 409、`status: error`，不会让旧页面或旧客户端误报成功。权限错误仍为403。

AstrBot原生父页面会把API业务错误转换为只含文字的JavaScript异常，丢掉结构化详情；即使HTTP改成200也不能直接解决。因此新管理页使用新增的`page/songs/upload-v2`入口：认证、校验与最终入库逻辑完全复用，只有**可处理的重复结果**采用成功传输信封，具体业务结果明确为未保存：

```json
{
  "status": "ok",
  "data": {
    "upload_conflict": {
      "code": "duplicate_audio",
      "saved": false,
      "message": "曲库已有相同原音……未保存重复文件。",
      "match_count": 1,
      "duplicates": [{"filename": "示例.wav", "name": "示例", "enabled": false}]
    }
  }
}
```

新页面先检查`upload_conflict`并显示定位入口，只有收到实际保存的`filename`才显示上传成功。自定义v2客户端也必须检查业务结果，不能只凭HTTP 200或外层`status: ok`判断已保存。正常上传仍返回已有曲目记录格式。详情最多8首，不包含摘要或服务器绝对路径。

两个入口都先做登录和来源检查。未登录、跨站修改等仍返回403，不读取、查询或返回曲库详情。没有放宽权限，也没有修改AstrBot父页面或SDK。
